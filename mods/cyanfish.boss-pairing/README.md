# 最终攻势 · 随机配队（`cyanfish.boss-pairing`）

## 这个 Mod 做什么

基座（= 官方口径）在**最终攻势**（同盟第 14 回合；隐秘核心第 15 回合）里，把**存活玩家按座位两两配对**：

```
座位 0 + 1 → 战场 b1（0 号守左半边、1 号守镜像的右半边）
座位 2 + 3 → 战场 b2
…（奇数人时最后一位单独占一个战场，用 _s 模板）
```

⇒ 同一批人反复开局，队友**永远是同一批人**。本 Mod 把这一步换成「**每个 boss 回合开始时，按当时的实际存活人数随机挑队友**」。

## 它到底改了什么（一个字都不含糊）

只做一件事：往合并后的 `data/config.json` 里加一段计数表。

```json
{ "op": "add", "path": "bossPairing", "value": { "default": "random" } }
```

基座那一侧的接缝是 `server/match/bossPairing.js`（读取器）+ `server/match/finalAssault.js` 的 `bossPairGroups()`（唯一的调用入口）。
没有这张表时接缝恒返回 `null` ⇒ 走官方 `pairPlayers(alive)`，与官方**逐值相同**。

## 口径（三条，都是有意的）

1. **随机的只是「谁和谁一队」**：洗牌后两两成组，但**组内仍按座位升序** ⇒ 组内座位靠前的那位照样守左半边。
   2 人房的「队友」本来就无从选择，所以它连**左右都不会变**。
2. **不碰本局任何既有随机流**：随机数来自 `deriveSeed(matchSeed, 'bossPair:回合号')` 派生的一条独立小流。
   ⇒ 打开本 Mod 时敌人的**波次内容、商店、机变发卡、AI 决策逐值不变**，只有分组变；关掉它时连这条派生流都不创建。
3. **两个 boss 回合各随机一次**：第 14 回合与第 15 回合是两条派生流（回合号进 salt）。
   中途有人被淘汰 ⇒ 按新的存活集合重新分组（与官方同一套「存活才上战场」的逻辑）。

## 兼容性 / 风险

* **纯 L2 数据 Mod**：没有 `content/`（行为代码）、没有 `assets/`、没有 `client/`。客户端**不需要**装：分组由服务器算好后随对局状态下发。
* **与 `cyanfish.max-seats` 无依赖、可各自单独开关**：本 Mod **不写** `config.coop`。
  原因（为什么不是 `coop.bossPairing`）：平台的补丁语言里 `add` 要求目标不存在，而 `max-seats` 已经用 `add coop` 占住了 `coop`
  ⇒ 第二个 Mod 再往 `coop` 里 `add` 会在**没装 max-seats 时**因「中间键不存在」整包失败。两个可独立开关的 Mod 不能共用同一条 `add`。
  细节见 `docs/MODS.md` §4.13。
* **人数上限无关**：4 人房、6 人房、12 人房都按各自的存活集合随机；战场数仍是 `⌈存活/2⌉`，没有变化。
* **关掉它**：管理页停用即可，立刻回到官方「按座位配对」。
* 开发阶段：本 Mod 属于「让线上行为更接近官方/服主预期」的那一类，默认在测试实例与正式服都启用（见 `<开发期脚本>/deploy_base_023.py` 的四张表）。

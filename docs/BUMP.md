# 升级到新的官方版本：要改哪些地方（清单）

> 本仓是**跟着官方版本走**的。官方发了新版本（例如 0.2.6 → 0.2.7）时，按这份清单过一遍。
> ★ **不要**临时手改代码里的版本号 —— 版本号已经收敛成**单一来源**：仓根 [`VERSION`](../VERSION)。

---

## 0. 版本号在哪（单一来源）

| 谁 | 从哪读 |
|---|---|
| 两个工具（`apply-overlay` / `publish-scan`） | **优先读仓根 `VERSION`**；读不到才退到 `overlay/shared/constants.js` 的 `APP_VERSION` |
| 覆盖层自己 | `overlay/shared/constants.js` 的 `APP_VERSION`（这是**官方那一版**的值，改它是"重新对齐"的一部分） |
| 14 个 Mod | 各自 `mod.json` 的 `gameVersion`（★ 装载器**严格相等**校验：漏改一个，那个 Mod 会被整包跳过） |

---

## 1. 先把新版官方拿到手

- 官方仓库拉到新版本（或官方发行包），`package.json` 的 `version` 就是新版本号；
- 记下**官方这一版改了哪些文件**（对比上一版的官方差异）—— 第 4 步要用。

## 2. 换版本号（机械活，有脚本）

```bash
node tools/bump-version.mjs <新版本> --dry-run    # 先看会改什么
node tools/bump-version.mjs <新版本>              # 写 VERSION + 改 14 个 mod.json
```

它**不会**动文档 —— 它会把"文档里还写着旧版本号的行"**列出来**给你。

## 3. 过一遍文档（人过目）

按脚本列出的行，把**"当前对齐版本"**的说法改成新版本。判断标准：

| 该改 | 不该改 |
|---|---|
| 「本仓对齐/基于官方 **X**」「本体必须是 **X**」「示例目录 `Stronghold-Protocol-X`」 | **历史记录**（旧版本的更新说明、旧公告、CHANGELOG 历史条目） |

★ 写文档时**尽量少写死版本号**：需要点明的地方写一次，并加一句「**权威值见仓根 `VERSION`**」；
命令示例里用 `<官方目录>` 这类占位符，而不是把版本号焊进路径。

## 4. 重新对齐覆盖层（**这一步最容易漏**）

我们的 `overlay/` 是「**官方那些文件 + 我们的改动**」。官方新版**也改过**的文件，需要重新合并：

1. 找出**官方新版改动集 ∩ 覆盖层成员**（只动这几个，其余一个字节都别碰）；
2. 把新版的官方内容与我们的改动**合**进 `overlay/` 对应文件；
3. **重算 `overlay/ORIGIN.sha256`**：每个成员在**新版官方**里应有的 sha256（官方没有该文件的写 `ABSENT`）；
4. **重算 `overlay/MANIFEST.sha256`**：`overlay/` 里这些文件**自己的** sha256；
5. ★ **顺手脱敏**：新合进来的代码常会带上开发期的内部引用（本地脚本路径、内部工序号）——
   `publish-scan` 会**逐条报出来**，按它的 FAIL 清单改干净。

## 5. 自检（两道，都别省）

```bash
node tools/publish-scan.mjs --repo . --honor-exceptions   # 期望 PASS（FAIL 0）
node tools/apply-overlay.mjs --target "<新版官方目录>" --dry-run
#   期望：目标版本 = 新版本 ✓ · 闸① 覆盖层完整性 N/N · 闸② 冲突 0 · RESULT: OK
```

第二道是**最有力的验证**：它等于说「**官方原版新版本 + 本仓的包**真的能装起来」。

## 6. 记忆点

- **`VERSION` 是唯一权威**；工具不写死版本 ⇒ 升级时**不用碰工具代码**；
- **Mod 的 `gameVersion` 必须与本体严格相等** ⇒ 每次升级都要全部一起改（第 2 步的脚本就是干这个）；
- **覆盖层对齐**（第 4 步）才是真正的工作量；`ORIGIN` 不对齐 ⇒ 用户那边"闸②"会直接拒绝写入（这是**保护**）。
